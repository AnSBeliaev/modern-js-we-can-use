# Что из современного JS мы уже можем использовать

В рамках первой презентации мы разбирали, как фича попадает в стандарт и как проверить её стадию. Сегодня вопрос практический: что из современного JavaScript уже можно использовать в проекте.

## 1. Можно ли использовать фичу?

Обычно на этот вопрос отвечают процентом с сайта caniuse. У каждой возможности языка там своя цифра. У метода toSorted одна, у Object.groupBy другая. Цифра показывает, у скольких людей браузер уже понимает именно эту возможность.

Но эта цифра не говорит, можно ли нам использовать данный метод. Браузер посетителя получает не точно тот файл, который мы написали. Сначала проект собирают. Сборка берёт наши файлы и отдаёт браузеру уже другой JavaScript.

Какой получится код, решают две настройки. Первая — файл .browserslistrc. Там список браузеров, для которых мы собираем сайт. Вторая — поле target в tsconfig. Оно говорит, JavaScript какого года попадёт в готовый файл.

Цена в том, вырастет ли файл, который мы скачиваем. У разных фич она разная. Дальше три варианта.

Процент с caniuse ни в одном из трёх случаев не участвует. Сборка смотрит в наш список браузеров и в target.

## 2. Три категории фич с разной ценой

Сборка смотрит в список браузеров и в поле target, но с разным кодом поступает по-разному. Фичи здесь делятся на три категории, и цена у них разная.

Первый — новый синтаксис. Допустим, в target указан 2019 год. Записи name ?? 'гость' в том году ещё не было. Сборка пишет вместо неё проверку: если name не null, оставить name, иначе слово «гость». Такую проверку браузер 2019 года уже может прочитать. В файл полифилов эта запись не попадает. Проверка длиннее, и файл приложения из-за этого станет чуть больше.

Второй — новый метод, вроде toSorted. Переписывать нечего: точка и скобки старые, браузер понимает запись «вызови метод с таким именем». Сборка смотрит список браузеров до открытия сайта. Если у браузера из списка этого метода нет, готовая реализация попадает в отдельный файл. Этот файл скачивают все, даже те, чей браузер метод уже знает.

Третий — возможность браузера, вроде AbortController. Сборка строку не меняет и в файл полифилов функцию не кладёт. Если у браузера из списка этой возможности нет, вызов падает.

## 3. Синтаксис заменяется проверкой

Мы пишем name ?? 'гость'. Это новые знаки. Они значат: если name это null или undefined, подставить слово «гость». Браузер из нашего списка может этих знаков не понять. Тогда сборка заменяет их на обычную проверку: если name не null, оставить name, иначе взять 'гость'. После сборки строка будет чуть другая — примерно как в примере рядом.

Замену решают две настройки. Список в .browserslistrc отвечает, есть ли среди наших браузеров такой, который этих знаков не знает. Поле target в tsconfig отвечает, до какой старой записи сборке можно опуститься. Если в списке все уже понимают ??, строка может остаться как мы её написали.

Проверка длиннее одной строки name ?? 'гость'. Это и есть цена синтаксиса. Отдельный файл полифила за эти знаки не появляется: в готовом файле их просто нет.

## 4. Файл полифилов скачивают все

Сборку запускают один раз, до того как кто-то откроет сайт. Она читает .browserslistrc. Если в коде есть метод, которого нет у браузера из этого списка, готовая реализация попадает в отдельный файл. Посетитель скачивает его вместе со страницей. Скачивают все, и те, у кого браузер метод уже знает. Сборка заранее не знает, кто откроет сайт.

Сборка не переписывает вызов метода. Он остаётся в коде приложения. Для любого нового метода правило одно и то же.

## 5. Возможность браузера остаётся как есть

AbortController — возможность браузера отменить запрос. Это не проблема распознавания нового синтаксиса: строку new AbortController() браузер уже умеет читать, поэтому сборка не меняет её на другую. В файл полифилов функция тоже не попадает.

Если у браузера из .browserslistrc этой возможности нет, вызов падает. Сборка готовую функцию не подставит. Число и дату в нужном формате через Intl браузер либо умеет показать сам, либо нет.

## 6. Пример сборки и размеров

У нас в .browserslistrc стоит defaults, в target — es2023. Цифры в gzip: так файл едет по сети. Код приложения — 68,78 килобайта. Файл полифилов, когда toSorted в коде ещё нет, — 11,94 килобайта. Это не цена сортировки: sort — старый метод. Эти 11,94 килобайта сборка кладёт из-за других методов, которых не хватает браузерам из нашего списка.

Потом вызов заменили на toSorted и собрали ещё раз. Тот же файл стал 12,09 килобайта. Разница — 0,15 килобайта. Вызов остался в коде приложения, поэтому 68,78 не изменились. Дальше «используем / с полифилом / не берём» считаем именно для такого списка браузеров.

## 7. ES2016–2019 — уже все используют

Возведение в степень и includes, Object.values и entries, async/await, Promise.finally, flat — всё это уже давно есть во всех обычных браузерах. При нашем списке defaults их можно писать спокойно, отдельно решать «брать или нет» не нужно.

## 8. ES2020

Опциональная цепочка, нулевое слияние, Promise.allSettled, dynamic import, globalThis, BigInt — используем. В стандарт они попали в 2020-м, и браузеры их почти сразу подхватили. Если в target указан более старый год, сборка может заменить ?. и ?? на обычную проверку: файл чуть вырастет, но отдельный полифил за это не появляется.

## 9. ES2021

replaceAll, Promise.any, логические присваивания — используем. WeakRef и FinalizationRegistry не берём: нужны редко, с ними легко ошибиться. В обычном коде проекта их не пишем, даже если браузер уже умеет.

## 10. ES2022

at, Object.hasOwn, cause у Error, top-level await, поля класса и private-поля. Используем. Стандарт и поддержка в браузерах идут рядом. При нашем defaults всё это можно брать без оглядки.

## 11. ES2023

toSorted, toReversed, toSpliced, with и findLast / findLastIndex — только с полифилом. В стандарте 2023, в браузерах с июля 2023. Но в нашем defaults ещё остаются более старые версии — без готовой подмены вызов у них упадёт. Поэтому берём с полифилом. Сейчас разберём toSorted и типичный баг с sort в React.

## 12. Sort

На экране неотсортированный список. После нажатия кнопки «Сортировать» мы ожидаем, что порядок изменится, но этого не происходит. Метод sort мутирует массив и возвращает его же. setItems получает ту же ссылку, которая уже была на экране. React сверяет ссылки, а не порядок элементов внутри. Ссылка та же, поэтому React не видит изменений и не перерисовывает список.

## 13. toSorted

Если у браузера из списка нет toSorted, в файл полифилов попадает короткая реализация. Файл был 11,94 КБ, стал 12,09 КБ — плюс 0,15 КБ. Код приложения остаётся 68,78 КБ.

По кнопке список перерисовывается, потому что создаётся новый массив. toReversed, toSpliced и with устроены так же. В килобайтах мы замерили только toSorted.

## 14. ES2024

Object.groupBy, Map.groupBy и Promise.withResolvers — только с полифилом. В стандарте 2024, в браузерах с марта 2024. При defaults полифил всё ещё нужен. Сейчас — как groupBy упрощает группировку, а withResolvers — работу с промисом из кнопок.

## 15. Проблема создания категорий вручную

У нас есть массив с продуктами. Раньше, если нужна была группировка, её делали вручную. Яблоки и бананы должны попасть во фрукты, огурцы в овощи.

Код длинный, и группировка в нём теряется. Пустой массив для новой категории приходится создавать самим. Если этого не сделать, товар некуда положить, и код падает.

## 16. Object.groupBy собирает группы сам

Object.groupBy заменяет этот длинный код. Пустой массив создавать не нужно: метод сам раскладывает товары. Вся группировка — одна строка.

Ключ группы всегда строка. Для яблок и бананов это fruits, для огурцов vegetables. Если вместо категории вернуть число, метод преобразует его в строку.

В файл полифилов это плюс 0,16 КБ: было 11,94 КБ, стало 12,10 КБ.

## 17. Ключом Map.groupBy может быть объект

Те же товары. У Object.groupBy ключ только строка. Map.groupBy может взять ключом объект: для фруктов объект с названием «Фрукты», для овощей — «Овощи». Яблоки и бананы достаются вызовом get по объекту фруктов.

Отдельно это те же плюс 0,16 КБ в файл полифилов.

## 18. resolve вытаскивают из конструктора

Кнопки «Да» и «Нет» написаны отдельно от промиса. Ответа ещё нет, человек нажмёт позже, а код, который ждёт переменную answer, стоит на паузе. resolve('да') заканчивает паузу и передаёт строку «да». По кнопке «Нет» туда же уходит «нет». Внутрь конструктора кнопки не попадают, поэтому resolve раньше сохраняли во внешнюю переменную. Если присваивание забыть, ожидание так и висит.

## 19. withResolvers отдаёт resolve сразу

withResolvers сразу отдаёт промис и resolve. Внешняя переменная и присваивание внутри конструктора не нужны. В файл полифилов это плюс 0,14 КБ.

## 20. ES2025

Методы Set — intersection, difference, union — только с полифилом. В стандарт они попали в 2025-м, а в браузерах уже с июня 2024.

Promise.try можно брать с полифилом: с января 2025 он есть в свежих браузерах, удобно завернуть синхронный сбой в catch.

Error.isError и методы итераторов вроде take, map, toArray пока обходим: поддержка ещё неровная или кейс слишком узкий.

Ниже разберём только Set.

## 21. Сравнение списков через filter

Два списка сравнивают через filter. Для каждого тега из первого списка приходится заново пробежать весь второй. И так два раза: отдельно общие теги и отдельно теги только из первого.

## 22. intersection и difference

intersection и difference делают то же сравнение без ручного прохода. intersection оставляет js и css. difference оставляет react.

Имя intersection для сборки не повод класть полифил. Повод на этой строке другой: она видит new Set и вместе с ним кладёт в файл полифилов код методов.

## 23. union

Нужен один список из двух: 1, 2, 3 и 3, 4, 5, где тройка встречается один раз. Раньше списки сначала соединяли и получали 1, 2, 3, 3, 4, 5, потом убирали повтор. Если Set в середине забыть, ошибки нет, но тройка остаётся дважды.

union сразу собирает набор, где тройка одна. Полифил попадает в файл вместе с new Set, не из-за слова union.

## 24. С new Set в файл попадают методы

Без new Set кода метода в файле нет, и на браузере из списка без метода вызов падает. new Set сборка видит и вместе с ним кладёт intersection, difference и union. Если new Set в коде нет, эти три файла дописывают в настройке сборки.

## 25. Граница «можно брать» ≈ ES2025

До ES2022 пишем спокойно. ES2023–ES2025 — берём то, что реально упрощает код или убирает баг; при defaults рядом почти всегда поедет полифил. Узкое из ES2025 — Error.isError и методы итераторов — в общий код пока не тащим.

Год в стандарте и год в браузерах — разные вещи. Например, Array.fromAsync в стандарте числится как ES2026, а в браузерах есть с января 2024. Полифил заметный — около плюс 1,36 КБ. Решение «брать или нет» смотрим по поддержке и цене, а не по номеру года в названии стандарта.
